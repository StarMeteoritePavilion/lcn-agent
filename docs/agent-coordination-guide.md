# lcn-agent 后续 Agent 协作引导

## 1. 文档用途

这份文档用于指导后续 Agent 接手 `lcn-agent` 的学习、实现、任务分配和进度管理。
它规定接手顺序、状态判断、教学方式、验收证据和交接格式。

项目目录：`/Users/can/Projects/AI/lcn-agent`

最终目标：使用 TypeScript 和 Node.js，从零实现一个类似 Pi 的可扩展 TUI Agent。
项目采用“稳定核心 + 默认扩展 + 外部扩展”的结构，参考 Pi 的设计和固定源码版本，
不复制 Pi 源码。

参考项目目录：`/Users/can/Projects/AI/pi`

参考源码基线：`60e7e76bd7ea25cad1dd6f3f1ce0d18814a42759`

按照以下顺序读取：

4. 当前源码、配置和依赖文件：确认实际实现，不根据文档猜测。

## 3. 事实和状态的判断优先级

出现冲突时，按照以下优先级判断：

1. 用户最新的明确指令和实际终端输出。
2. 当前工作区中的源码、配置和测试文件。
3. 当前步骤文档中的目标和验收条件。
4. `docs/agent-development-learning-plan.md` 中的勾选状态。
5. Pi 固定版本源码及其测试中的参考行为。

计划文档是进度看板，不是实现事实。文件中存在一段代码，不等于学习步骤已经验收。
如果状态和证据冲突，先指出冲突，读取相关文件或等待用户补充，不得自行推断。

## 4. 学习模式和 Agent 职责

学习者熟悉 Java 后端开发，但 TypeScript 是新手。后续 Agent 作为指导者，遵循以下节奏：

1. 每次只推进一个足够小的步骤。
2. 先解释本步骤需要的 TypeScript 概念和必要的源码背景。
3. 提供需要修改文件的完整源码，由学习者手敲。
4. 解释源码中的关键语法、类型、调用顺序和运行结果。
5. 给出精确的验证命令、预期结果和一个小实验。
6. 等待学习者反馈实际输出和错误信息。
7. 根据反馈审查结果，确认通过后再更新勾选状态。
8. 未经用户明确要求，不直接替学习者修改实现代码。

后续 Agent 可以修改学习计划和教学文档，以记录状态或纠正事实；修改源码前必须得到用户明确授权。

## 5. 勾选状态规则

项目统一使用 `[ ]` 和 `[x]`：

| 状态 | 含义 | 使用条件 |
| --- | --- | --- |
| `[ ]` | 未完成或未验收 | 没有完整证据闭环，包含“代码已写但尚未运行验证” |
| `[x]` | 已完成 | 学习者已运行指定命令并完成实验，指导者已核对结果 |

以下情况不能标记 `[x]`：

- 只有源码，没有学习者的实际运行输出。
- 只有 `npx tsc --noEmit`，没有该步骤要求的运行或实验结果。
- 只有旧的 `dist` 输出，当前源码没有重新编译。
- 只有 Agent 自己的推断，没有文件或终端证据。
- 阶段内仍有任何子步骤或阶段验收项未完成。

“代码已写入，待运行验证”应保持 `[ ]`，并在下一行写明等待的验证内容。
阶段总览只有在该阶段的交付物和全部验收项完成后才能改为 `[x]`。

## 7. 后续任务拆分方式

每次任务只处理一个可验证的学习单元。任务描述至少包含以下字段：

| 字段 | 要求 |
| --- | --- |
| 目标 | 说明本次只学习或实现什么 |
| 文件 | 写出精确的相对路径或绝对路径 |
| 前置 | 列出已经完成的步骤和对应证据 |
| 概念 | 说明本次引入的 TypeScript 或 Agent 概念 |
| 源码 | 提供需要学习者手敲的完整文件源码 |
| 验证 | 给出命令、预期输出和退出结果 |
| 实验 | 安排一个能验证理解的小改动 |
| 通过条件 | 说明什么情况下可以标记 `[x]` |
| 下一步 | 只说明紧邻的后续单元，不提前展开实现 |

推荐的阶段 0 顺序如下：

1. 类型收窄：当前已完成，状态以第 6 节为准。
2. `Promise`、`async/await` 和异常传播。
3. 异步生成器和 `for await`。
4. `AbortController` 和取消传播。
5. 阶段 0 的完整小程序验收。

完成阶段 0 后，再进入模拟模型和工具调用循环。没有完成模拟循环前，不接入真实模型、TUI 或 MCP。

## 8. 每一步的验收流程

收到学习者反馈后，按以下顺序检查：

1. 读取当前源码，确认实验代码是否已经恢复。
2. 对照步骤文档和计划中的精确目标。
3. 核对用户提供的完整命令、输出、错误类型和退出状态。
4. 必要时执行只读检查，例如读取文件、运行类型检查或查看生成文件。
5. 区分“命令通过”和“整项验收通过”；不能用一个命令替代全部条件。
6. 只有证据闭环后才把对应条目改为 `[x]`。
7. 在计划中记录简短证据，避免只留下无来源的勾选。

对于代码步骤，至少核对：

- 当前源码是否与要求一致。
- TypeScript 类型检查是否通过。
- 运行结果是否符合预期。
- 小实验是否产生了预期错误或行为。
- 实验代码是否恢复，恢复后的检查是否通过。

## 9. 任务分配和并行协作

默认由一个 Agent 负责当前学习步骤，避免多个 Agent 同时修改同一工作区。
需要审查时，可以分配只读任务，要求审查 Agent 不修改文件、不提交、不运行外部副作用操作。

适合分配的只读任务包括：

- 核对某个步骤的文件、命令和状态是否一致。
- 阅读 Pi 固定提交中的指定源码和测试，整理可验证事实。
- 检查文档引用、链接、勾选状态和行宽。

任何涉及源码修改的并行任务，都必须先明确文件边界、互不覆盖，并在合并前重新读取工作区差异。
学习者手敲的未提交修改必须保留，不能使用破坏性 Git 命令清理工作区。

## 10. 交接记录格式

任务完成或暂停时，后续 Agent 使用以下格式记录：

```text
任务：<本次学习单元名称>
状态：已完成 / 待验收 / 阻塞
修改文件：<精确路径列表；没有修改时写“无”>
已确认：<用户输出或文件证据>
验证命令：<实际执行的命令>
验证结果：<实际输出、错误类型和退出状态>
计划更新：<哪些条目从 [ ] 变为 [x]，或保持 [ ] 及原因>
下一步：<只写紧邻的下一学习单元>
```

“阻塞”只在当前工作无法继续且需要用户提供具体文件、输出或授权时使用。
不能把尚未完成、等待反馈或需要继续学习写成已完成。

## 11. 交付前检查

后续 Agent 结束一次任务前，必须确认：

- 没有把未验收的源码改动标为 `[x]`。
- 没有根据标识符、路径、字段或 API 名称的大小写和格式进行猜测。
- 没有覆盖学习者的未提交修改。
- 没有把 Pi 的参考实现表述成 lcn-agent 已实现能力。
- 没有提前引入下一阶段的复杂依赖或抽象。
- 计划、步骤文档和实际证据之间不存在未说明的冲突。
